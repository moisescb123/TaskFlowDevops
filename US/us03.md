## Original

Como Admin quiero registrar usuarios y asignarles un rol (Admin, Desarrollador o Visor) para controlar quién puede configurar, modificar o solo consultar el sistema.

## Enhanced

**Story:** As an Admin, I want to register users and assign each one a role (Admin, Developer, or Viewer) so that I control who can configure the system, modify tasks, or only view the board.

**Priority:** High (required before meaningful multi-user login/board use)

**Related:** US01 (login), US02 (logout), US08 (assignee must be a registered user), RNF03, RNF05

### Behavior

1. Authenticated **Admin** opens the user management screen.
2. Admin submits a new user: **email**, **password**, **full_name**, and **role**.
3. Backend validates input, ensures email uniqueness, hashes the password, and persists the user in SQLite.
4. On success, the new user appears in the user list (without the password) and can later sign in (US01) with the assigned role.
5. Non-Admin callers (Developer, Viewer, or anonymous) cannot create users (`403` / `401`).
6. Admin can list users to verify registrations and to support assignee selection elsewhere (Developers may get a reduced list for assignees; full management UI is Admin-only).

### Fields and validations

| Field | Rules |
|-------|--------|
| `email` | Required; valid email; unique; sanitized |
| `password` | Required; non-empty; stored only as `password_hash`; never returned in responses |
| `full_name` | Required; non-empty; sanitized |
| `role` | Required; one of `admin`, `developer`, `viewer` |

- Invalid/missing fields → `400` with clear field-level messages (RNF03).
- Duplicate email → `400` (or `409` if preferred; default `400` aligned with current API spec).
- Password must never appear in logs, list responses, or `User` JSON.

### Acceptance criteria

- **AC1:** Given an Admin with valid user data, when they create a user, then the API returns `201` with `id`, `email`, `full_name`, and `role` (no password).
- **AC2:** Given a duplicate email, when Admin submits create, then the request is rejected with a clear error and no user is created.
- **AC3:** Given a missing/invalid field or invalid role, when Admin submits create, then the API returns `400` with a clear validation message.
- **AC4:** Given a Developer or Viewer, when they call `POST /api/users`, then the API returns `403`.
- **AC5:** Given an unauthenticated caller, when they call `POST /api/users` or Admin UI, then access is denied (`401`).
- **AC6:** Given a newly created user, when they log in with the provided credentials (US01), then the session reflects the assigned role.
- **AC7:** Given Admin opens user management, when users exist, then `GET /api/users` lists them without password hashes.

### Endpoints (from `docs/api-spec.yml`)

- `POST /api/users` — body `UserCreate` `{ email, password, full_name, role }` → `201` `User` / `400` / `403` / `401`
- `GET /api/users` — list users → `200` `User[]` / `401` / `403` (Admin for full management; reduced assignee list may be allowed for Developer per API notes)

### Files / modules to touch (expected layout)

- `app/routes/users.py` — `POST/GET /api/users` with Admin authz
- `app/services/user_service.py` — create user, hash password, uniqueness checks
- `app/models/user.py` + SQLite access — persist `User`
- `templates/admin/users.html` + `static/js/admin_users.js` — Admin registration UI
- Authz decorator/middleware — Admin-only for management routes
- `tests/test_users_admin.py` — Pytest for AC1–AC7

### Definition of done

- [ ] Admin UI to register users and assign role
- [ ] Password hashing; no plain-text storage or API leakage
- [ ] Role enum enforced: `admin` | `developer` | `viewer`
- [ ] Authz: only Admin can create/manage users
- [ ] Pytest covers success, validation, duplicate email, and forbidden roles
- [ ] `docs/api-spec.yml` and `docs/data-model.md` remain consistent

### Non-functional requirements

- **Security (RNF05):** Hash passwords; sanitize inputs; Admin-only authorization
- **Usability (RNF03):** Clear validation and duplicate-email messages
- **Persistence (RNF02):** Users survive application restart in SQLite
- **Maintainability (RNF01):** Keep authz and user creation in service layer, not templates
- **CI:** User-admin tests included in Pytest / GitHub Actions

### Role impact

| Role | Capability in this story |
|------|--------------------------|
| Admin | Register users, assign roles, list users for management |
| Developer | Cannot register users; may later use user list only for assignee picking (US08) |
| Viewer | No access to user management |

### Out of scope (this story)

- Edit/deactivate users or change roles after creation (future story if needed)
- Self-registration / public sign-up
- Login and logout flows (US01, US02)
- Password reset
